## E1 控制面往返时延

协议说明：每次请求新建 TCP 连接，所以测量值包含 **TCP 三次握手（1 RTT）+ 请求应答（1 RTT）≈ 2 RTT**。

| 路径 | 请求 | n | median | p95 | max | CSV |
|---|---|---|---|---|---|---|
| 本机（家用 WiFi）→ VPS | `@get_list` | 1000 | **92.94 ms** | 110.35 | 156.90 | `e1_local-lan.csv` |
| 本机（家用 WiFi）→ VPS | `@ask_addr/1003` | 1000 | **93.16 ms** | 110.49 | 281.00 | 同上 |
| 重庆校园网 → VPS | — | — | "差不多"（未记录精确值） | — | — | — |
| 北京移动数据 → VPS | 待测 | — | — | — | — | — |

**已填入论文**：Table III 前两行（92.9 / 156.9 与 93.2 / 281.0），
以及 VII-B 里"两跳 RTT 占 60–100 ms、服务项几毫秒"的论证。

**ICMP 基线**：`ping 111.228.32.155` 为 **30–50 ms**，VPS 在**华北**。

### 关键推断（已写进论文）

93 ms ÷ 2 = 46.5 ms，落在 ping 的 30–50 ms 区间内 ⇒ 控制面时延 ≈ **2 个链路 RTT**，
服务项只有几毫秒。所以：

- 在同一城市部署也救不了这个数：瓶颈是**到中继的链路**，不是地理位置差异
- 重庆那条"差不多"因此是自洽的——两条路径 RTT 本就接近
- 唯一异常值是 `@ask_addr` 的 281 ms，判定为 TCP 握手重传（只出现在一种请求上，
  两种请求的中位数只差 0.2 ms）

### 尚未解释的观察

用户报告 **~50 个 session 时出现瓶颈**。机制上说得通：每个 session 一个忙轮询线程，
50 个线程在 2 核上抢会调度饥饿。但**没有实测数字**（CPU%、饱和点、timer drift 频率）。

VII-D 目前仍是占位符。要么补测（E6），要么把那段改成定性描述并删除具体数字。

**观察**
- 93 ms ≈ 2 RTT，反推到 VPS 的基线 RTT 约 **45–50 ms**。这个数需要用 `ping` 核实。
- `@ask_addr` 的 max（281 ms）明显高于 `@get_list`（157 ms），像是单次 TCP 重传或调度抖动；
  如果 ping 显示没有丢包，正文可以加一句"the maximum corresponds to a single
  retransmission of the TCP handshake"。
- **标签问题**：本轮的 `--label local-lan` 是误称。中继是公网 VPS，本机到它走的是互联网，
  不是局域网。后续标签改用 `host-wifi`。论文里**不能出现 LAN**，否则与部署不符。

## 诊断记录

| 观测 | 数值 | 含义 |
|---|---|---|
| 3 个 host 时中继线程数 | **9** | 结构对得上（main + msg accept + 4 IOCP + app + 3 session），**无线程泄漏** |
| 1 个活跃 session 时 `@get_list` | 93 ms | 见下 |
| 北京本机 vs 重庆校园网 | 两者"差不多" | 路径差异被某个恒定项盖住，或两条路径 RTT 本来就接近 |

**（已推翻）** 原先推断"93 ms ≈ 2 × 46 ms 的链路 RTT、路径主导"是错的：
链路其实是 10.3 ms，93 ms 里 61 ms 是 Nagle 停顿。见下面"重要修正"。

**注意**：这与"~50 个 session 时出现瓶颈"并不矛盾。忙轮询的代价随活跃 session 数线性增长，
少量 session 时看不出来，50 个 session 在 2 核上就会导致调度饥饿，此时服务项才膨胀。

### 【重要修正】链路 RTT 是 10.3 ms，不是 40 ms

`ping` 在 VPS 上 **100% 丢包（ICMP 被过滤）**，所以之前口头给的 "30–50 ms" 不成立。
改用应用层自己的 UDP `@id` 往返作为基线：

| 量 | 值 | 来源 |
|---|---|---|
| **UDP 链路 RTT** | **10.3 ms** | `diag_control_split.py`，n=20 |
| TCP connect | 27.8 ms | 同上（min 11.5 / max 29.5） |
| 请求 → 长度头 | 10.6 ms | 同上 |
| **长度头 → 正文** | **61.0 ms** | 同上（59.2–64.4，极窄） |
| 控制面合计 | 98.9 ms | 同上 |

**根因**：`msg::send_with_head` 里两次独立 `send()`（4 字节长度头 + 正文），
没有 `TCP_NODELAY` → 第二段被 Nagle 压住等延迟 ACK。61 ms 占控制面总时延的 62%。

**修法**（3 行）：把长度头和正文拼成一个缓冲区一次 `send()`，或对 accept 出来的
socket 设 `TCP_NODELAY`。论文按"报告缺陷"写，未做修复后的对比。

### E4 数据面附加时延

| 量 | 值 |
|---|---|
| 探测包数 | 1000（@ 50 pps） |
| **往返中位数** | **18.5 ms** |
| p95 / max | 20.8 / 62.0 ms |
| 四段单程理论值 | 2 × 9.2 = 18.4 ms |
| **丢失** | **0 / 1000** |

结论：18.5 ≈ 18.4，**中继自身处理开销低于测量分辨率**；1000 个包全部到达。
E4 的模型（4 段单程）与 UDP 基线互相印证，两个独立实验对上了。

### 【关键结果】Nagle 修复前后对照（同一机器、同一链路）

把 `msg::send_with_head` 的两次 `send()` 合并成一次之后重测：

| 阶段 | 修复前 | 修复后 |
|---|---|---|
| TCP 握手 | 27.8 ms | 25.6 ms |
| 请求 → 长度头 | 10.6 ms | 10.9 ms |
| **长度头 → 正文** | **61.0 ms** | **0.0 ms**（20/20 全是 0.0） |
| **合计** | **98.9 ms** | **36.0 ms** |
| UDP 链路 RTT | 10.3 ms | 9.2 ms |

**这是一个干预实验**：机制预测"合并写入后那 61 ms 会消失"，改一个函数，
61 ms 精确归零，总计降 64%。论文 VII-B 已按 before/after 重写，Table III 两块并列。

剩余结构：26 + 11 ≈ 2 个 RTT，其中握手占 2.8 个 RTT（链路只该 1 个），
归因于接入网中间盒，代码层改不掉。

### E6 扩展性（三个版本的演进）

第一次跑 E6 时中继在 10 个 session 就崩了。修了四处才走到最终版：

1. `session_list` 加 `std::mutex`（msg 线程读 / app 线程 erase，无同步 = use-after-free）
2. `tick_timer` 改成锁内只改表、**锁外再 destroy()**（join 不能持锁）
3. `is_running` 改 `std::atomic<bool>`
4. `domain()` 的等待方式：忙轮询 → `sleep_for(1ms)` → **`select()` 阻塞**

三个版本的表现：

| 版本 | 20 个 | 50 个 | 100 个 | 数据面 RTT |
|---|---|---|---|---|
| 忙轮询 | 误回收 | — | — | 18.5 ms |
| sleep(1ms) | 0 | 0 | **68 次误回收** | **33.9 ms**（+15.6 ms，Windows 时钟粒度） |
| **select()（最终）** | 0 | 0 | **0** | **16.1 ms** |

最终版五档实测（`e6_scaling.csv` + `e6_high.csv`）：

| 并发 session | 误回收事件 | 单样本最少存活 | 列表中位 | 列表最大 |
|---|---|---|---|---|
| 20  | 0 | 20/20  | 40.2 ms | 51.9 ms |
| 50  | 0 | 50/50  | 40.1 ms | 69.5 ms |
| 100 | 0 | 100/100 | 42.7 ms | 65.4 ms |
| 200 | 0 | 200/200 | 52.0 ms | 80.8 ms |
| 300 | 0 | 300/300 | 49.3 ms | 108.5 ms |

**结论：到 300 个都没找到饱和点。** 中位几乎不动（40→49 ms），只有长尾在涨（52→109 ms），
这是 2 核上排队等待就绪线程的正常表现。

论文 VII-D 已改成"三个版本"的叙事，并以"未测到上限"作结，不再声称 principal engineering debt。

**已填入论文**：Table III 第四行（`2.2\,s` / `2.8\,s`），以及 VII-B 里
"eight matches ... every sample fell below the bound" 那段。

**结论**：8 个样本全部落在 [1.41, 2.76] s，**没有一个超过 3 s 上界**，
而且都接近典型值 2 s —— 与修正后的推导（计数器崩溃时通常为 2，需 2 次递减）
完全吻合。原先论文里"4 秒上界"的写法是错的，已被这组数据推翻并改正。

**注意**：n=8 偏少。论文里的辩护是"该量由构造决定上下界、不是估计分布，
所以关键是没有任何样本越界"。如果审稿人要求更多样本，补跑到 20–30 次即可，
数字不会变（这是个被硬编码的窗口约束住的值）。
